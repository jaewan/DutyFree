## What T4 is for

T4 exists to produce **one restorable checkpoint of a booted guest whose running
kernel carries the streaming mechanism**. Nothing else. It is not a measurement,
it produces no number the paper may cite, and no performance statement is
licensed by it.

### One warning was worth chasing: `instruction 'wbinvd' unimplemented`

A cache-maintenance instruction that gem5 does not implement is exactly the kind
of thing that would make a streaming transition look free because the simulator
skipped it. Traced, and it is **not** the streaming path:

- streaming's transition flush is `clflush_cache_range()`, called once from
  `mm/streaming.c:322`. It does not use `wbinvd`. The `wbinvd_on_all_cpus` /
  `wbnoinvd_on_all_cpus` helpers in `arch/x86/lib/cache-smp.c` are generic and
  are not on this path.
- the `wbinvd` warnings come from ordinary boot/PAT initialization.
- `clflush` **is** modeled. `CLFLUSH_M`/`CLFLUSH_P` expand to the `clflushopt`
  microop plus `mfence`, and `clflushopt` is a real store-op carrying
  `Request::CLEAN | Request::INVALIDATE | Request::DST_POC`
  (`src/arch/x86/isa/microops/ldstop.isa:667`). Zero `clflush` warnings in the
  boot log.
- the Ruby path recognizes it too: `Sequencer.cc` branches on
  `pkt->isCleanInvalidateRequest()` at two sites, and CHI carries
  `SnpCleanInvalid` machinery.

**Limit, stated rather than glossed:** what is established is that the request
type is decoded and recognized, not that a guest `clflush` has been traced
end-to-end through CHI to the HNF and observed to invalidate. T4 booted with
`--caches`, the classic hierarchy; T5 restores into Ruby/CHI. If the cost or
effect of the transition flush ever becomes load-bearing, that trace is the work
to do, and it has not been done.

This is an apparatus finding — whether the simulator models the operation — and
not an attribution of the AMD CAT residual between H2 and H3. It is outside the
§3 δ embargo, which in any case does not cover the streamer-side cost of
flush-behind.

## Addendum, 2026-08-24 03:23 — the 90-minute zero-byte-`stats.txt` tripwire fired, and why that is not a failure

W8's operating rules carry a tripwire: a gem5 run whose `stats.txt` is still
zero bytes after 90 minutes is to be treated as suspect. T4 launched 01:25. At
02:55 the tripwire condition was true, and it is still true now at 03:23, at
1 h 54 m elapsed. Recording the disposition rather than letting it pass in
silence, because a tripwire that is quietly ignored once stops being a tripwire.

**The tripwire does not apply to this run shape, and the reason is structural.**
gem5 writes `stats.txt` when the stat system is dumped, and for a boot-and-
checkpoint pass that happens at `simulate()` exit. Nothing dumps stats during
the boot: there is no periodic dump configured and the rcS is `empty.rcS`, which
issues no `m5 dumpstats`. A zero-byte `stats.txt` is therefore the *expected*
state for the entire duration of T4, not a symptom. The tripwire is a valid
liveness test for a run that dumps periodically; it is uninformative for one
that dumps only at exit, and T4 is the latter.

**The liveness evidence that does apply**, all read read-only at 03:22:53:

| evidence | observation |
| --- | --- |
| process state | pid 2069959, `R`, 99.9% CPU, 01:53:55 elapsed |
| guest console | advanced to `W8-GUEST checkpointing...` (last write 03:02) |
| checkpoint `m5.cpt` | 344,082 bytes, 03:02 |
| `store0.pmem` | 14.2 MB, complete 03:02 |
| `store1.pmem` | 254.1 MB, complete 03:15 |
| `store2.pmem` | 13.0 MB at 03:16 → 85.7 MB at 03:22, ~12 MB/min |

The run is not merely alive, it is producing the artifact the gate is waiting
for. G-T4-4 and G-T4-6 remain open on their own terms; nothing here pre-empts
them.

## Consequence for T5, fixed now rather than after the fact

T5's arms restore and run a benchmark, and they also dump stats only at exit.
The same tripwire will nominally fire on any T5 arm that runs longer than 90
minutes, which under O3 + Ruby/CHI is likely. Deciding then what counts as
"hung" would be choosing a criterion with the run in front of me, which is the
§6.6 failure. So it is fixed here, before any arm starts:

1. **Alive and working**: the gem5 process exists and its accumulated CPU time
   is advancing between checks. A gem5 that is merely blocked shows this
   immediately.
2. **The real hang guard is Ruby's, not mine.** A CHI protocol deadlock is
   *loud*: Ruby's deadlock detector panics rather than spinning silently. So the
   hang mode this tripwire was written to catch is already covered by the
   simulator, and its absence from the log is positive evidence.
3. **Wall-clock timebox**, not a liveness test: T5's three arms remain inside
   W8's stated budget, and overrunning it is an escalation to the lead, not a
   decision to make here.

This is honestly a **weaker** test than the one it replaces, and it is worth
saying so plainly: it cannot distinguish "simulating correctly" from
"simulating something wrong quickly". It is the strongest test available for a
run that emits nothing until it finishes. If a T5 arm needs a stronger one, the
right fix is to configure a periodic stats dump so the original tripwire becomes
applicable again — that is a real option, and it is not being taken now only
because it would change the apparatus mid-campaign.
