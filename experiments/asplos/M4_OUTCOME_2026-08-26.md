## Both registered readings fire the failure branch

**Primary.** Rate rises **14.5×**; the non-residency floor rises **1.20×**
(1.070 → 1.279). The registered threshold for "queueing near saturation" was
>20×; for "proportional to traffic" 7–20×; **<3× is "the rate-dependence rescue
FAILS."** It is 1.20.

**Secondary, independently decisive.** The residency share is
**30.8 / 29.2 / 28.9 / 27.3 / 27.6%** — a spread of **3.5 points** across the
whole 14.5× range, against a registered ±15-point threshold. The share does not
depend on rate.

So the three conflicting decomposition points — W5.3-Intel ~100%, M3b/M4 ~28%,
AMD 76% — are **not one curve in rate.** The reconciliation the panel and I both
reached for is unavailable, and it was unavailable for a reason we can now state:
the non-residency component is essentially fixed, not congestion.

## What the model is now, stated honestly

> Neighbour harm decomposes into a **residency** component that declining to
> allocate removes, and a **rate-invariant non-residency** component that it does
> not. On this configuration the split is ~28/72 and holds across a 14.5×
> range of stream rates. **Why the split differs between configurations —
> ~100% for a pure streamer on Intel SPR, 76% for a pure streamer on AMD, 28% for
> a fused tenant on Intel EMR — is unexplained.** The two-component structure is
> supported; the covariate that sets the split is not identified.

That is a hypothesis with three supporting retrodictions and **one unexplained
counter-point**, and it must be written that way. It is not a law and the paper
may not present it as one.

## The obvious candidate, and why it is not yet claimed

What is constant across 1→16 workers while rate rises 14.5×? **F's hot table** —
256 MiB at every worker count. And flush-behind flushes the *fact array* only; it
never touches the table, which F is actively using and which must stay cached.

That would reconcile W5.3 without any appeal to rate: its aggressor was a **pure
stream with no reuse structure**, so its harm was all stream residency and a
capacity control reached 1.00×. F carries a second resident working set that no
stream-scoped mechanism can address.

**But the AMD point contradicts it.** That aggressor was also a pure streamer with
no table, and its post-flush floor was still **2.30×**. Either AMD's floor is a
different cause — plausible, since E3 established AMD's harm is rate-class where
Intel's is capacity-class — or the table hypothesis is wrong.

**Unregistered, and not claimed.** One cheap test decides it: run the same sweep
with F's hot table shrunk to 4 MiB. If the floor collapses, the floor is F's
table. Registered as M5 before running.

## What this does to the paper

The mechanism's measured value is unchanged and now better bounded: it removes
**~28%** of neighbour harm in this configuration, stable across a 14.5× rate
range, at zero new architectural state and zero cost to the tenant. The *reason*
the fraction is 28% here and 76% elsewhere is open.

The honest framing is the frontier already recorded in `M3B_OUTCOME` Addendum 1
§A6: non-allocation is one point on a trade-off, not an escape from it. M4 adds
that the point is **stable in rate**, which is genuinely useful — a mechanism
whose yield does not collapse under load is more deployable than one whose does —
and subtracts the story that would have explained the spread.
