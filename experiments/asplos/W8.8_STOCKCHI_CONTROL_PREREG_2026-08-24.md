# W8.8 — The stock-CHI control: pre-registration

**Written 2026-08-24, before the control build finished and before any control
datum existed.** Sections 1–8 are fixed as of that moment. The result goes in a
dated addendum below, never by editing what follows.

Follows W8.7 and its addendum 2, which closed with: "Reproduce on a

the question with consequences beyond W8."

---

## 1. The question

T5 arm 2 (`stream_mprot`) does not stall in the benchmark. It stalls in the
guest kernel, with both cores spinning in `queued_spin_lock_slowpath` on the
same lock (`0xffff8881077e4df0`, reached via `_raw_spin_lock_irqsave` ←
`__wake_up`), the lock word frozen at exactly `0x00000001` — locked, **pending
and tail clear**. Two CPUs in the slowpath must set those queueing bits. They
never do, across samples ~6 minutes of wall apart at unchanged PCs. Their
atomic read-modify-writes are taking no effect, which is also why the run
commits zero `MemWrite`.

Our branch modifies `src/mem/ruby/protocol/chi/`. "That is upstream's bug, not
ours" is therefore not available for free. The question is whether our CHI
edits cause the forward-progress failure.

This matters beyond W8. If our CHI protocol edits can wedge atomics, every
Ruby/CHI number this project owns is in question.

## 3. What in our delta could actually have executed — the gating audit

This is the part that makes the control interpretable rather than merely
suggestive, so it is recorded before the run.

Every functional change in the 221-line delta is gated on one of two flags:

* `is_streaming` / `tbe.isStreaming` — `needCacheEntry`'s new bypass clause,
  `CheckCacheFill`'s `!(is_HN && tbe.isStreaming)`, `Allocate_DirEntry`'s H3
  branch, the `isStreaming` propagation in `AllocateTBE_SeqRequest`,
  `AllocateTBE_PfRequest`, `Initiate_Request`, `prepareRequest`,
  `Finalize_UpdateCacheFromTBE`, and `Initiate_Replacement`'s copy from the
  cache entry.
* `sf_finite` — `getDirEntry`, the new `dirTagPresent` / `dirDeallocate`
  helpers, `Allocate_DirEntry`'s finite branch, the whole `CheckSFFill` action,
  the `SF_Eviction` transitions, `Initiate_SF_Eviction`.

Both are off in the aborted run, and this is verified from the run's own
artifacts rather than assumed:

* all 24 `streamingTranslations` / `streamingAccesses` stat lines are **0** in
  the aborted run (32 lines, all 0, in the gdb diagnostic re-run). Nothing was
  ever tagged. The stall is *before* `declare_streaming()` is called.
* `config.ini` reports `sf_finite=false` and
  `enable_H3_streaming_bypass=false` on **every** controller. `HNF_SF_FINITE`
  and `HNF_H3` are unset on the T5 path.

Three further changes are ungated but provably inert:

* `Deallocate_DirEntry` and `Finalize_UpdateDirectoryFromTBE` now route through
  `dirDeallocate` / `dirTagPresent`, whose `sf_finite == false` branches are
  textually identical to the code they replaced.
* the new `if (in_msg.isSFEvict)` arm added *first* in `replTriggerInPort` —
  which now runs on every replacement trigger. `isSFEvict` is declared
  `default="false"` and the single site that sets it true is inside
  `CheckSFFill`. Checked because an undefaulted bool read on the mainline
  eviction path would have been exactly this class of bug; it is defaulted.
* new SLICC events/transitions enlarge the generated tables but do not alter
  any existing `(state, event)` pair.

## 4. The single ungated functional change

One line, in `Initiate_Replacement` (`CHI-cache-actions.sm`):

```slicc
  if (initial == State:UD_RU) {
    tbe.dataBlk := cache_entry.DataBlk;      // upstream
    tbe.dataBlkValid.fillMask();             // upstream
    tbe.dataValid := true;                   // OURS — ungated
  }
```

Added as the "H3/B2 FIX" for silent dirty-data loss on the SF-eviction path.
It fires on **every** UD_RU replacement regardless of streaming or finite-SF,
so it is live in the aborted run. `UD_RU` — locally unique-dirty with a remote
unique holder — is the state a contended lock line occupies while it bounces
between two cores, and `tbe.dataValid` is read at several downstream sites
including `CheckCacheFill`'s `need_fill`.

Whether that is the mechanism is not asserted here. What is asserted is that it
is the *only* candidate our delta offers for this run.

## 5. Prediction, registered before the run

From §3 and §4: the control differs from the aborted run in exactly one
executable line. So the control should **stall identically** — same 248-byte
console truncated mid-word after ` ent`, same frozen lock word — unless
`tbe.dataValid := true` is the cause.

## 6. Outcome branches and what each licenses

**B1 — control reproduces the stall.** Our CHI edits are exonerated. The
forward-progress failure is upstream gem5 CHI's, exposed by this workload's
timing. W8's Ruby/CHI numbers are not put in question by it. Decisive, and this
is the branch §5 predicts.

**B2 — control completes the run.** Then the difference is the one line in §4,
and §3 makes that inference far stronger than a bare "stock behaved
differently" would be: with everything else gated off, there is no other
executable difference to attribute it to. This would be a real bug in our
protocol edit and would have to be fixed and every affected Ruby/CHI result
re-examined. Follow-up already specified: rebuild with **only** that line
reverted (nothing else) and confirm it alone flips the outcome.

The asymmetry that would normally weaken B2 — "a different protocol perturbs
timing as much as a re-rolled seed would, so completion proves nothing" — is
what §3 is for. It is weakened, not eliminated: §3 argues semantic equivalence,
not cycle-for-cycle timing equivalence, and SLICC table layout differs. B2
therefore still requires the one-line confirmation before it may be reported as
causation.

**B3 — anything else** (fails to launch, crashes, stalls somewhere different,
stalls at a different console length). Reported as its own outcome. It is
**not** to be filed under B1 or B2. W8.7's discriminator already produced a
fourth, unenumerated outcome; that must not be smoothed over a second time.

## 7. Detection criteria, fixed in advance

Read off `logs/fs_restore_chi/w8_t5_CONTROL_stockchi_2026-08-24/`:

* **reproduced** — `system.pc.com_1.device` reaches exactly **248 bytes** and
  ends `... bytes=4194304 ent`, and stays there while `simTicks` advances, with
  the `MemWrite` delta between two stat dumps **zero on both cores**. The
  reference signature is cpu0 `MemWrite` 64,200 / cpu1 3,162,502, which the gdb
  re-run already reproduced bit-identically.
* **not reproduced** — the console passes 248 bytes, i.e. emits `ries=262144`.
* Either verdict is reachable well inside an hour of wall clock. Restore alone
  costs ≈9.6 min (derived from arm 1: 6491 s wall vs 5913.74 `hostSeconds`).

## 8. What this control does not settle

* It does not decide whether arm 2 can be made to run. B1 in particular says
  the bug is upstream's, not that it is gone.
* It licenses **no** performance comparison. The control is not an arm, and it
  is deliberately named so that `t5_analyze.py` refuses to gate it — `arm_spec()`
  matches by suffix, and `…CONTROL_stockchi_2026-08-24` ends in no `ARMS` key,
  so it reports `UNKNOWN ARM … not gated` (the W8.7 §6 quarantine, reused).
* Arm 3 (`stream_m5op`) stays barred and T2 stays unlaunched: arm 2's gate has
  not passed.

## 9. Apparatus notes

`fs_restore_chi_8592.sh` derives `ROOT` from `BASH_SOURCE`, so running the
worktree's copy makes `GEM5`, `FS`, `--chi-config`, `KERNEL`, `CKPT` and `OUT`
all worktree-relative with no env override and no edit to the launcher.

One edit was required in the control tree's `configs/ruby/CHI_config_8592.py`:
stock `chi/` does not declare `sf`, `sf_finite` or
`enable_H3_streaming_bypass`, which that config sets at five sites, so the
control would have failed to launch for a reason unrelated to the hypothesis.
Each site is wrapped in a `_hasp()` guard that skips the assignment when the
protocol does not declare the param, and asserts on any name outside those
three so the guard cannot mask a typo. All three are off on the T5 path (§3),
so the guard is behaviour-preserving. The edit exists **only in the control
worktree**; `~/DutyFree/gem5/configs/ruby/CHI_config_8592.py` is unchanged.
