# W8 / T2: the "next authorized measurement" already ran, was truncated on all
# three arms, and reported success

Found 2026-08-24 while clearing T2's deferral (its blocker — W7 host
contention — cleared when W7 drained at 04:46). **T2 was not started.** What
follows is why it must not be started as specified.

This is **F12** — an artifact read and believed that does not do what it says —
in the runner the T2 audit itself names as the next authorized measurement.

## 1. What the audit prescribed

`benchmarks/e2e/hash_join/GEM5_FS_OS_CONTRACT_T2_AUDIT.md`, verbatim:

> The next authorized measurement is a bounded, serial matched trio at 53%,
> executed by `gem5/scripts/intel_8592_4cpu_dirtax_streaming_supervised.sh`.
> That runner uses the exact frozen command-line geometry, records provenance
> per arm, and sends `SIGINT` after 5,400 seconds if an arm still has zero-byte

The audit is otherwise careful and correct: it identifies the nine SIGINT'd arms
of the historical 15-way sweep, tabulates exactly which six completed, and states
"No conclusion about tax, H2, H3, or the OS contract follows from these partial
artifacts." Nothing here contradicts it. The defect is in what happened next.

## 2. That trio ran on 2026-08-23. All three arms were killed.

`gem5/logs/intel_8592_4cpu_dirtax_streaming_supervised/20260823T111437Z_53p/`.
From the arms' own `provenance.txt`, unedited:

| arm | started | tripwire fired | finished | exit_status | simTicks |
|---|---|---|---|---:|---:|
| alone | 11:14:38 | **12:44:38** | 12:44:42 | **0** | 193,114,613,248 |
| with_agg | 12:44:42 | **14:14:42** | 14:14:46 | **0** | 48,669,197,266 |
| with_streaming | 14:14:46 | **15:44:46** | 15:44:50 | **0** | 51,941,415,388 |

Every arm carries `tripwire_reason=zero-byte_stats_after_5400s`. Every arm's
`run.log` ends:

```
Exiting @ tick <N> because user interrupt received
```

## 3. Why it came back green

`run_arm`'s success test was:

```bash
[[ $status -eq 0 && -s "$arm_out/stats.txt" ]]
```

**gem5 handles SIGINT by dumping a complete stats file and exiting 0.** So each
killed arm produced 1.8–2.0 MB of entirely normal-looking statistics, exit
status 0, and passed the test. The tripwire was recorded in `provenance.txt` and
*nowhere else* — not in the exit status, not in the control flow, not in
anything a reader of `stats.txt` would ever see. The runner then proceeded to
the next arm and reported the trio done.

**The arms stopped at 193.1e9 / 48.7e9 / 51.9e9 ticks — roughly 4× different
amounts of work.** A matched trio whose members did different amounts of work is
not a trio. Had these numbers been analysed, the "DirTax" they showed would have
been an artifact of when each arm happened to be killed.

## 4. Root cause: the timeout is shorter than a known completion time

This is not a marginal miss. From the historical sweep, in the repo since
2026-08-23:

```
logs/intel_8592_4cpu_dirtax_streaming/alone_53p   hostSeconds 6072  (1.69 h)  COMPLETED naturally
```

**6072 s > 5400 s.** The tripwire was set below the observed completion time of
the fastest arm of the very configuration it was guarding, so the `alone` arm
was guaranteed to be killed before it could finish. The contended arms are
strictly slower, and the historical sweep measured how much slower — at
~17,400 s they had reached only 40% and 44% of `alone_53p`'s tick count:

| arm | ticks at 17,400 s | rate | to reach 431.8e9 (a **lower** bound) |
|---|---:|---:|---:|
| with_agg_53p | 172.5e9 | 9.91e6 t/s | **≥12.1 h** |
| with_streaming_53p | 191.8e9 | 11.03e6 t/s | **≥10.9 h** |

431.8e9 is a lower bound on the target because the victim runs a fixed `ITERS`
and contention *raises* its per-iteration tick cost, so a completed contended arm
must exceed `alone`'s total, not match it.

**A serial 53% trio therefore costs on the order of 25–30 host-hours, not the
4.5 h the 5400 s × 3 budget implied.** The budget was off by ~6×.

## 5. Fixed today (apparatus, not results)

`gem5/scripts/intel_8592_4cpu_dirtax_streaming_supervised.sh`:

* **A tripped arm now fails.** Two independent detectors — a marker file written
  by the watchdog before it signals (the watchdog is a subshell and cannot set a
  variable in `run_arm`), and a grep for gem5's own `because user interrupt
  received` in `run.log` (which also catches a manual Ctrl-C). Either one sets
  `completed=no`, `run_arm` returns 1, and it prints
  `Its stats.txt is NOT a result. Do not analyse it.`
* **The trio aborts at the first failed arm** with exit 3, instead of spending
  hours producing a comparison that cannot be made.
* **`provenance.txt` gains `tripwire_fired`, `user_interrupt`, `completed`.**
* **Default `TIMEOUT_S` raised 5400 → 50400 (14 h)**, with the derivation in §4
  written into the file at the assignment. 14 h clears the ≥12.1 h lower bound
  with margin.

Verified against the real 2026-08-23 artifacts, which is the only test that
matters here — old test vs new test on the three truncated arms:

```
  alone            old test: PASS    new test: FAIL
  with_agg         old test: PASS    new test: FAIL
  with_streaming   old test: PASS    new test: FAIL
```

Both invalid run directories now carry `INVALID_DO_NOT_ANALYSE.md`.

## 7. What I did NOT do, and what the lead has to decide

**T2 was not launched.** Under the W8 rule "escalate rather than decide … spending
beyond the timebox," a 25–30 host-hour serial trio is a spend decision.

Three options, with the recommendation stated:

1. **Run the trio concurrently, not serially.** *Recommended.* ~12 h wall instead
   of ~25–30. Serialization was adopted because the historical 15-way sweep
   "lost its children when the invoking command ended" — a **supervision**
   failure, not a contention one — and it costs validity nothing to undo: gem5
   is deterministic in simulated time, so host load moves wall clock and not
   `stats.txt`. That is the same argument already used to run W7 and T5
   concurrently. Three gem5 processes on a 256-core host at load 1.3 is not
   contention. *(Not implemented — implementing it is part of the decision.)*
2. **Run it serially at the corrected 14 h timeout.** ~25–30 h, one host, no
   change of design.
3. **Drop the 53% point.** T2 does not gate T3 or T4, and the audit already
   records that nothing follows from the partial artifacts. The cost is that
   W8 ships with no DirTax trio at a WSS where the predicted tax exists — the
   10% trio is complete and matched but, per the audit, "the predicted tax is
   at larger WSS," and its three runtimes are 1.000× at printed precision.

## 8. What this does not change

No published number moves. The historical sweep was already correctly quarantined
by the T2 audit, and the supervised trio's numbers have never been reported
anywhere — this memo is their first and last appearance. No paper edit follows.

What it does change is a standing assumption: **"the runner reported success" has
not been evidence in this project, and now it is.** The same question should be
asked of any other runner with a watchdog. `run_t5.sh` has no watchdog at all —
its tripwire was a manual check, recalibrated in `W8.4` — so T5 is not exposed to
this defect, but it is also not protected by anything automatic.

## Addendum, 2026-08-24: the repo-wide watchdog sweep §8 asks for

Section 8 above says "the same question should be asked of any other runner with
a watchdog." This addendum answers it. Nothing above is altered.

**Question.** Can any other runner in this repo report success for a run it
killed — the F12 in §1–§6?

**Method.** Grepped every tracked script for `kill -INT|kill -9|kill -TERM|
timeout|TIMEOUT_S|tripwire`. The ~40 hits under `linux/tools/testing/selftests/`
are upstream and not ours. Seven of our own runners matched; each was read at the
line where the child's outcome is decided.

| runner | watchdog | outcome test | verdict |
|---|---|---|---|
| `gem5/scripts/intel_8592_4cpu_dirtax_streaming_supervised.sh` | `kill -INT` at `TIMEOUT_S` | *was* exit status + non-empty `stats.txt` | **the F12 — fixed this session** |
| `benchmarks/experiments/cat_mba.py` | `subprocess.run(timeout=)` | `TimeoutExpired` uncaught, then `if r.returncode != 0: raise` | clean |
| `benchmarks/experiments/wss_sweep.py` | `subprocess.run(timeout=)`; `proc.wait(timeout=10)` then `kill()` on the aggressor | `if r.returncode != 0: raise RuntimeError` (`:149`); separate `RuntimeError` on aggressor readiness (`:134`) | clean |
| `experiments/phase1/e1_residual_decomp/run_e1_gate.py` | none on the victim | **returncode never checked** | latent, visible-failure — see below |
| `…/run_e1_a4a5.py` | none on the victim | same | same |
| `…/run_e1_a6.py` | none on the victim | same | same |
| `experiments/asplos/exp35_smba_pareto.sh`, `exp36_localdram_ccx.sh` | — | no matches at all | n/a |

**The three `run_e1_*` runners share one latent defect, and it is not this one.**
`vproc = subprocess.run(...)` has no timeout and its `returncode` is never
examined (`run_e1_gate.py:192-202`, `run_e1_a4a5.py:172-180`, `run_e1_a6.py:115-122`).
A victim that died would leave `victim_line = ""` through the
`next((… ), "")` fallback, `parse_victim("")` returns `{}`, and the record's
`cyc_per_iter` becomes `None`. That is a **visible** failure — a null in the
artifact — not a success report over a killed run. It is the opposite failure
mode from the gem5 one, and for a structural reason worth naming: **gem5 emits a
complete, plausible `stats.txt` when signalled** (`Exiting @ tick N because user
interrupt received`, exit 0), so a killed gem5 arm is indistinguishable from a
finished one by exit status or file size. A killed silicon victim emits nothing,
and nothing is loud. The F12 needed a child that lies convincingly; only gem5 does.

**Did it ever fire? No.** All twelve `e1_residual_decomp` data files were scanned:
684 records carry the nested `victim` schema, and **0** have an empty `victim` or
a null `cyc_per_iter`. The remaining 96 (`clean_ccx1_n12.jsonl`) use a flat schema
with no `victim` key at all, and all 96 carry a populated `cyc_per_iter`.

No fix is applied to the three `run_e1_*` runners. They are phase-1, their
campaigns are complete, the defect has demonstrably never fired, and its failure
mode is a visible null. Editing a frozen runner to protect against a fault it did
not have would change apparatus for no measurement.

**A false positive of my own, recorded because it is the same class of error.**
The first scan reported 96 bad records. The scan was wrong, not the data: its
condition was `cyc_per_iter is None or not r.get("victim")`, and the second clause
fires on every record of a schema that has no `victim` key. An analyzer that
reports a defect it invented is F12 pointed the other way, and it was caught only
by opening one of the 96 records it flagged. **Read one flagged record before
believing a count.**

**Result.** The kill-reported-as-success defect was confined to the one runner,
which is fixed. `run_t5.sh` still has no watchdog, as §8 states.
