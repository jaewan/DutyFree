# W8.7 — T5 arm 2 (`stream_mprot`) livelocked in the guest and was killed

**2026-08-24.** Arm 2 started 05:24:30, killed 12:08:14, **6 h 44 m**, no result.
Its output directory has been renamed
`w8_t5_stream_mprot.ABORTED_GUEST_LIVELOCK_2026-08-24` and carries a
`README_ABORTED.txt`. **Arm 2's gate has not passed. Arm 3 is not started**, per
W8's standing rule: do not start task N+1 until task N's gate has passed and you
have said so in writing. This memo is that writing, and it says the gate failed.

## 1. What was observed

The guest console stops **mid-word**, at

```
...bytes=4194304 ent
```

Arm 1 — same binary, same rcS structure, same checkpoint — continues that line
`entries=262144 anon_huge_kb=0 kernel_page_kb=0 mmu_page_kb=0`. The truncation
is inside the `HOT_TABLE` `std::cerr` chain at `cxl_join_bench.cpp:1537-1544`.
Last console byte 05:42:53: **6 h 18 m of the run produced no output at all.**

## 2. What the simulator was doing

Diagnosed in order, each step ruling out one class of cause:

| probe | result | rules out |
|---|---|---|
| host load, memory | healthy | host exhaustion |
| two `SIGUSR1` stat dumps, 75 s apart (12:04:03, 12:05:18), each serviced in ~2 s | event loop alive | a wedged simulator |
| `simTicks` 328,600,703,316 vs arm 1's **complete** run at 233,720,202,636 | simulated time advancing | a stalled clock |
| committed instructions between the two dumps: **+17,229,000** | the guest is executing | a deadlock |
| total committed 5,399,028,304 vs arm 1's complete 233,171,614 | **23×** arm 1's whole run | "just slow" |

`SIGUSR1` was only sent after confirming gem5 installs a handler for it
(`init_signals.cc:443`, `SIGUSR1 → dumpStatsHandler`); the default disposition
would have killed the run. A serviced dump is positive evidence the event loop
is alive, not merely an absence of bad news.

**The decisive counter is the instruction mix.** Between the two dumps the delta
was byte-identical on both cores — `IntAlu 7,657,333` each, `MemRead 957,167`
each, **no stores**, exactly 8 `IntAlu` per `MemRead`. Two cores lockstepped in
one 8-instruction, store-free polling loop. Arm 1 at the same point was
asymmetric (cpu0 59,750,906 / cpu1 173,420,708). This is a **livelock**, not a
deadlock and not slow progress: the guest is spinning, productively executing
nothing.

`hostTickRate` was 14,031,038 against arm 1's ~39.4 M ticks/host-s — 2.8× slower,
which is a *consequence* of two cores hammering the memory system, not a cause.

The guest PC could not be recovered: `remote_gdb.cc:418: warn: Sockets disabled`.
See §5.

## 3. What this does and does not implicate

The stall is at `:1537`. `declare_streaming()` is called at `:1548`. **Arm 2
never reached its declaration.** Therefore:

- **Ruled out as proximate cause:** the `mprotect(PROT_READ|PROT_STREAMING)`
  call, the PTE readback, and anything downstream of the declaration. The code
  that hung is byte-identical to arm 1's, which completed.
- **NOT ruled out:** the STREAMING kernel. `CONFIG_PAT_STREAMING=y` in the
  booted `vmlinux`, so `mm/streaming.c`'s hooks are compiled in and live on
  every page fault of this run. Arm 1 passing shows the same kernel *can*
  complete, not that it always does.
- **Also not ruled out:** anything generic — a busybox/ext2 interaction, an
  O3+CHI restore artifact, a two-core race in the bench's own startup.

The honest statement is that **the cause is unknown**, and W8.6's own standard
applies to it: an unexplained stall is not evidence for or against any claim.
Nothing here may be cited about `PROT_STREAMING`.

## 4. A naive retry is futile, and this is why

gem5 is deterministic in simulated time. `RUBY_RANDOMIZATION=1` selects gem5's
**default RNG seed 5489** (documented at
`scripts/intel_8462y_4cpu_dirtax_streaming.sh:11`). Same checkpoint + same rcS +
same seed → identical execution. **An identical re-run reproduces this livelock
bit-for-bit and burns another ~7 hours to fail the same way.** Re-running
unchanged is not a diagnostic; it is a 7-hour no-op.

Note also that `RUBY_RANDOMIZATION=1` is **hardcoded into the `exec env` line**
of `fs_restore_chi_8592.sh` and cannot be overridden from the environment.
Changing it requires editing committed apparatus.

The one cheap fact this buys: the hang occurred **18 m 23 s** into the run
(05:24:30 → 05:42:53). Determinism means any diagnostic reproduction reaches the
hang point in **~18 minutes**, not 7 hours.

## 5. The diagnostic that is available without editing apparatus

`fs_restore_chi_8592.sh` sets `GEM5=${GEM5:-$ROOT/build_Intel_8592/gem5.opt}`
and expands `$GEM5` **unquoted** in its `exec` line. Extra gem5 top-level flags
can therefore be injected purely from the environment — precisely the mechanism
`run_t5.sh`'s header documents ("everything W8 needs that differs from the
committed launcher is supplied through the environment"). So

```
GEM5="$G/build_Intel_8592/gem5.opt --listener-mode=on"
```

enables the remote-GDB socket that `remote_gdb.cc:418` reported disabled, with
**no file edited**. Attaching with `vmlinux`'s symbols at the hang point yields
the spinning PC and a kernel backtrace, which is the difference between "unknown
cause" and a decidable question. Cost: ~20 minutes of one host.

This is a **diagnostic** run. It computes no gate, produces no arm, and its
output directory must be named so it can never be mistaken for one.

## 6. Technique recorded: suffix-rename quarantine

The aborted directory is an **F12 hazard in waiting**: gem5 exits 0 on SIGINT
(`Exiting @ tick 5884839458616 because user interrupt received`) and leaves a
`stats.txt` with three plausible-looking dump sections. Nothing about it looks
broken.

`t5_analyze.py`'s `arm_spec()` matches arm names by **suffix**
(`name.endswith(k)`) — a deliberate choice so directories may be freely
*prefixed*. The dual of that choice is a free quarantine: **appending** a suffix
makes the analyzer report `UNKNOWN ARM … not gated` and refuse to score the
directory. Verified after the rename. No analyzer edit, no deletion, data
preserved for the post-mortem, and the reader cannot be tricked into quoting it.

## 7. Status and what is owed

- Arm 1 (`wb`): **PASS** (W8.6).
- Arm 2 (`stream_mprot`): **FAILED TO RUN.** Not a gate failure of the mprotect
  path — a failure to reach it.
- Arm 3 (`stream_m5op`): **not started**, and must not be.

Arm 2 is the arm that carries W8's capability demonstration, which underpins
**L4** (OS-enforceable). Its blocker is therefore escalated to the lead rather
than decided here, per W8's instruction to escalate anything that would alter
what the paper claims. The options, with costs:

1. **Diagnostic reproduction with `--listener-mode=on`** (§5). ~20 min, no
   apparatus edit, answers the actual question. Recommended first step, and
   strictly informational — it commits to nothing.
2. **Perturb the seed.** Would require editing the hardcoded
   `RUBY_RANDOMIZATION=1`, i.e. a mid-campaign apparatus change. The apparatus
   rule's own wording — "beyond the minimum required to run at all" — arguably
   licenses it, since arm 2 cannot run at all. But re-rolling nondeterminism
   until an arm completes, without knowing what it was doing, is close enough to
   §6.6's fishing that it should not be done *before* option 1.
3. **Perturb the rcS.** Changes a pre-registered arm script. Worst of the three:
   same blind re-roll as (2), and it damages the arm's identity.

**Recommendation: option 1, then decide.** Options 2 and 3 both spend a
~7-hour arm on a guess; option 1 costs 20 minutes and may make the guess
unnecessary.

T2 remains unlaunched pending the lead's separate decision on its spend.

## Addendum, 2026-08-24 — a hypothesis registered before the gdb data exists

The diagnostic of §5 is running (`--listener-mode=on` via the `GEM5`
environment override, no apparatus edited; gdb listener up on 127.0.0.1:7000,
CPU0 only). It has not yet reached the hang. This section is written **now**, so
that the reading of the backtrace cannot be chosen after seeing it (§6.6).

### The hypothesis: the console wedged, not the workload

`std::cerr` is unbuffered, so each `<<` is its own `write()`. In the chain at
`cxl_join_bench.cpp:1537-1545` the literal `" entries="` is **one 9-byte write**.
The console stopped after ` ent` — **4 bytes of 9**. A write that delivers part
of a single short literal and then never completes is not a workload that
stopped computing; it is a guest blocked *inside* the tty write path,
mid-string.

That matches the instruction mix exactly. The 8250 console driver emits one
character at a time and polls the LSR transmitter-holding-register-empty bit
between characters (`wait_for_xmitr`). That is an **MMIO load poll with no
stores** — precisely the observed signature: `MemRead` with exactly 8 `IntAlu`
per read and **zero stores** across 17.2 M committed instructions.

If true, the livelock is in gem5's UART model or the guest's 8250 driver, has
nothing to do with STREAMING, `mprotect`, or the workload, and arm 2's failure
carries no information about the paper's claims at all.

### The competing hypothesis, registered so this is not a one-story test

Both cores showed **byte-identical** deltas (`IntAlu 7,657,333`, `MemRead
957,167` each). A store-free poll loop is also what the kernel's idle poll
(`cpu_idle_poll`, spinning on `need_resched`) looks like. So an equally
consistent story is: one core wedged somewhere, the other idling in a poll loop
— or both in the idle poll with the workload thread never scheduled.

### The discriminator, fixed now

On reaching the hang, resolve `$pc` on CPU0 against `vmlinux`'s symtab
(`.debug_info` is absent — symbol names only, no source lines) and, if `$pc` is
a user address, against the static guest binary
`build/cxl_join_bench.gem5fs` (2,911 text symbols).

- **CONSOLE hypothesis CONFIRMED** if `$pc` lands in
  `wait_for_xmitr` / `io_serial_in` / `serial8250_console_putchar` /
  `serial8250_console_write` / `console_*` / `vprintk*`.
- **IDLE hypothesis CONFIRMED** if `$pc` lands in `cpu_idle_poll` /
  `do_idle` / `mwait_idle*`.
- **BOTH REFUTED, and the finding becomes material**, if `$pc` lands in
  `mm/streaming.c` symbols, in the fault path, or in bench userspace
  (`build_table`, `smaps_info`, allocator).

Only the third outcome would bear on the paper. The first two would make arm 2's
6 h 44 m a harness failure and nothing more — which is the outcome to *expect*,
not to hope against.

**Caveat on binary identity.** The guest's `/root/cxl_join_bench.gem5fs` could
not be checksummed against the host build (`debugfs` is unavailable here), so
userspace symbol resolution is provisional until that is closed.

**Caveat on the reproduction.** The diagnostic carries one deviation from arm 2 —
`--listener-mode=on` — which opens sockets at init. It should not perturb
simulated execution, since nothing connects until the hang, but if the run
*completes* rather than hanging, that deviation is the first suspect and the
determinism argument of §4 would need revisiting.

## Addendum 2, 2026-08-24 — the diagnostic answered it: a kernel spinlock livelock

The §5 diagnostic ran and the stall **reproduced exactly**. Recorded against the
discriminator fixed in addendum 1, which was committed before this data existed.

### The reproduction is bit-identical, so §4's determinism argument holds

| | aborted arm 2 | diagnostic |
|---|---|---|
| console at stall | 248 B, truncated mid-word after ` ent` | **248 B, identical truncation** |
| cpu0 `MemWrite` | 64,200 | **64,200** |
| cpu1 `MemWrite` | 3,162,502 | **3,162,502** |

`--listener-mode=on` did not perturb the execution. The caveat registered in
addendum 1 is therefore closed in the direction that *keeps* §4: an unchanged
re-run reproduces this hang.

### What the guest was doing

**Both cores were spinning in `queued_spin_lock_slowpath`**, on the **same
lock**, `0xffff8881077e4df0`. Thread 1's stack:

```
#0  queued_spin_lock_slowpath
#1  _raw_spin_lock_irqsave
#2  __wake_up
```

The lock word read **exactly `0x00000001`** — locked, with the **pending bit and
tail clear** — in samples taken ~6 minutes apart, with both cores at unchanged
PCs (`+22` and `+24`) and `rax = 1` (their `cmpxchg` failing) on both.

Three things follow, and the third is the finding:

1. Neither core holds the lock; both are spinning for it.
2. A spinlock is held by a *running* CPU with preemption off. With both CPUs
   spinning, **no one holds it** — yet the word never clears.
3. Two CPUs in the slowpath must set the pending/tail bits. Those bits are
   **clear and stay clear**. Their atomic read-modify-writes are **not taking
   effect on memory at all.**

That also explains the signature §2 rests on: a perpetually failing `lock
cmpxchg` retires no store, which is why 17.2 M instructions committed with
**zero** `MemWrite`, and why both cores' deltas were byte-identical — they are
executing the same handful of instructions in the same loop.

### Scored against the registered discriminator — honestly, none of the three matched

Addendum 1 fixed three outcomes: CONSOLE (`wait_for_xmitr`, `serial8250_*`,
`console_*`, `vprintk*`), IDLE (`cpu_idle_poll`, `do_idle`, `mwait_idle*`), or
MATERIAL (`mm/streaming.c`, the fault path, bench userspace).

**The result is a fourth outcome I did not enumerate**: a kernel spinlock
livelock in a wakeup path. It must be reported as such rather than filed under
the nearest registered branch. It is *adjacent* to CONSOLE — `__wake_up` on a
waitqueue is consistent with the tty write path, and the stall is mid-`write()`
— but `__wake_up` is generic kernel infrastructure and I did not name it in
advance, so claiming the console branch "basically matched" would be exactly the
post-hoc fitting the pre-registration exists to prevent.

An intermediate sample, taken before the run reached the stall, found cpu0 in
`mwait_idle` and cpu1 in `build_table()+448`. That is a **healthy** run mid-
compute, not the hang, and it is recorded here only so it is not mistaken later
for evidence: my 240 s-console-quiet detector cannot distinguish a hang from
long silent compute, because `build_table` prints nothing.

### Does it bear on the paper?

**Almost certainly not, but this is not fully closed.** The stall is in generic
kernel locking, not in `mm/streaming.c`, not in the fault path, and before any
declaration. Against that:

- Our gem5 branch (`w8-streaming-counters`) **does** modify the coherence
  machinery — `CHI-cache{,-actions,-funcs,-ports,-transitions}.sm` — so "it is
  upstream's bug, not ours" is **not** a claim I can make.
- But every H3 / finite-snoop-filter gate defaults **off**
  (`HNF_H3=0`, `HNF_SF_FINITE=0`) and the T5 launch path sets none of them;
  `HNF_DMT=1` is the calibrated baseline used by every prior run. The STREAMING
  LLC bypass acts only on tagged lines and **nothing is tagged at the stall
  point**.
- The strongest control already in hand: **arm 1 completed on this exact
  protocol build**, so it is not globally broken. What arm 2 changes is timing.

Read together: a latent atomics/forward-progress failure in the simulated
machine, which arm 2's timing happens to hit and arm 1's does not. That is a
**harness failure**, and arm 2's 6 h 44 m yields no evidence for or against any
claim in the paper. It is *not* a result about `PROT_STREAMING`.

The residual risk worth naming: if the forward-progress bug is in **our** CHI
edits, it is a credibility question for every Ruby/CHI number the project owns —
not because those numbers are wrong, but because we would be shipping a
protocol we know can livelock. Deciding whether to chase that is a lead call.

### Options now, revised by the evidence

Options 2 and 3 of §7 (re-roll the seed, perturb the rcS) are now clearly the
wrong shape: they would paper over a simulator forward-progress bug by hunting
for a timing that dodges it, and the run that "succeeded" would be
indistinguishable from one that got lucky. What the evidence supports instead:

1. **Reproduce on a stock-protocol build** to settle whether our CHI edits are
   implicated. This is the question with consequences beyond W8.
2. **Check the atomics path directly** — the lock word never changing under
   `lock cmpxchg` is a specific, testable claim about the CHI protocol's
   handling of locked RMWs.
3. Only then decide how arm 2 should be run.

All three are lead calls. Arm 3 remains barred; T2 remains unlaunched.
