# W4.5 — provenance correction for the SF campaigns, and what the artifacts actually establish

Written 2026-08-24. **Re-analysis and file forensics; zero compute cost.**
Corrects three statements in documents committed earlier today
(`W1.5`, `W3.4`) and one in `W1.4`. Two corrections tighten a claim that was
too loose; one loosens a caveat that was too tight.

This was found while self-testing `analyze_sf_fin.py`, which unexpectedly ran
to completion because the 2026-08-20 data is still in `/tmp`. Directory
timestamps then contradicted the provenance tables I had written hours earlier.

## What the surviving artifacts do establish

F10 is the loss of the *launcher*. It is worth being precise about what a
launcher decides and where else that decision is recorded, rather than treating
"launcher gone" as a uniform blackout. For `sf_*`, the launcher decides:

| launcher decision | recorded in the surviving artifacts? |
|---|---|
| simulator binary | version banner in every run log |
| `--outdir` | the directory path itself |
| `COMMON` gem5 flags | yes — resolved into `config.ini` |
| workload + arguments | yes — `cmd=`, `executable=` in `config.ini` |
| `HNF_SF_FINITE`/`SETS`/`WAYS` | yes — `sf_finite`, `assoc`, `size`, `num_leaves` |
| `HNF_H3` | yes — `enable_H3_streaming_bypass` |
| `HNF_DMT` | yes — `enable_DMT`, `enable_DMT_early_dealloc` |
| `RUBY_RANDOMIZATION` | yes — `randomization=ruby_system` |
| **`SEED`** | **no — the seed values are gone** |

Exactly one decision is unrecoverable. Per SS6.6 the seeds are gone and stay
gone; nothing below is an attempt to guess them.

**One simulator binary, for all 24 runs.** Every log reports
`gem5 compiled Aug 9 2026 07:55:19`, v25.1.0.1.
`build_Intel_8592/gem5.opt` has mtime 2026-08-09 12:51:35. The last commit
touching `src/` is `56874f1d42` (2026-08-09 07:25:21), which the build
postdates, and **no `src/` commit has landed since** — so the binary is not
merely consistent across the campaigns, it is current with respect to HEAD's
compiled code. `356e7b7d0e` (2026-08-19 09:27:15) changed only
`testcase/dutyfree/aggressor.c`.

**One config tree.** `configs/` is Python, read at run time, so it is *not*
frozen by the build — but its last change is `fa103c5b7b` (2026-08-19 09:26:59),
before both campaigns. The empirical check is stronger than the git one:
`config.ini` records the resolved configuration, and `sf_h2_fin_s1`
(2026-08-20) vs `sf_h2_inf_s1` (2026-08-23) differ in **exactly four lines**,
all in the snoop-filter block — `sf_finite` true/false, `assoc` 16/1, `size`
4194304/1024, `num_leaves` 16/1 — which is precisely the arm difference. That
diff spans the date gap directly.

**Workload binaries are byte-identical rebuilds of committed source.** Rebuilt
today with the committed `Makefile` recipe (gcc 15.2.0, `-O3 -static
-march=x86-64 -ftree-vectorize` for the aggressor, `-O1 -static -march=x86-64`
for the others) into `/tmp` — the in-use binaries were not touched:

| binary | in-use mtime | md5 (in use == rebuilt) |
|---|---|---|
| `aggressor` | 2026-08-19 00:23:21 | `9a9695d5c5304c5d7e16278aa26770b0` |
| `victim` | 2026-07-30 07:05:25 | `c9c87195fbf43241f7149a27b1a0a353` |
| `dummy` | 2026-07-30 07:05:25 | `45d9a8596b3fd14a9daa3dcb312956be` |

The aggressor's mtime is ~9 hours *before* the commit that last changed its
source, which looked like a discrepancy. It is not: the binary is bit-identical
to a build of the committed file, so it was built from the same content before
that content was committed.

**Randomization was on and the seeds differed.** Not from a launcher — from the
data. Per-arm `cpu0.numCycles` across `s1/s2/s3`:

| arm | s1 | s2 | s3 |
|---|---:|---:|---:|
| `sf_qui_inf` | 101,596,284 | 101,673,625 | 101,663,139 |
| `sf_wb_inf` | 139,095,218 | 139,030,075 | 139,294,864 |
| `sf_wb_fin` | 254,500,212 | 254,182,021 | 254,105,047 |

Three distinct values per arm, so `RUBY_RANDOMIZATION=1` was active with three
distinct seeds in both campaigns. Which seeds is unknown and unrecoverable.

**The two campaigns share a bit-identical quiescent baseline.** This is the
sharpest cross-campaign check available, and it was not designed as one.
`sf_qui_fin_s*` and `sf_qui_inf_s*` are genuinely different runs — their
`config.ini` differ at `sf_finite=true/false`, `assoc` 16/1, `size` 4194304/1024,
`num_leaves` 16/1 — yet their cycle counts agree **to the cycle** at every
seed (101,596,284 / 101,673,625 / 101,663,139 in both). `SF_Eviction` is 0 in
both: the quiescent workload never pressures the snoop filter, so finite and
infinite are the same machine for it.

Two consequences. First, W1.4's single "victim alone" row being used as the
baseline for both the finite and the infinite table is now *verified* rather
than assumed. Second, a run from 2026-08-20 and its counterpart from the same
batch reproduce each other exactly under a deliberate configuration change,
which is what one would want a cross-campaign control to show.

## What this licenses, and what it does not

**Licensed: the finite/infinite H2+H3 agreement can stop being hedged on
provenance grounds.** Recomputed today from the stats:

| | cyc per victim L2 demand miss |
|---|---:|
| H2+H3, **infinite** SF | 152.24 |
| H2+H3, **finite** SF | 151.06 |
| difference | **−0.78%** |

`W1.5:144-151` hedges this as "a 0.7% agreement across a provenance gap of that
size is not a number to lean on," where "that size" was four days and a gem5
commit. The gem5 commit does not exist; the gap is one simulator binary, one
config tree, three byte-identical workload binaries and a four-line config
delta. The hedge should be withdrawn as stated. The claim it guards — *with H3
present, the victim's per-miss cost stops depending on whether the snoop filter
is finite or infinite* — is supported by the data, at one geometry, with the
usual caveat that no seed is shared between the two arms.

**Not licensed: calling the campaign reproducible.** Nothing above recovers a
launcher, and `analyze_sf_fin.py` cannot re-run these cells; it can only read
them. `sf_fin_cells.sh` (written today) will reproduce the *geometry* on a fresh
run, and its header says explicitly that it does not recover the 2026-08-20
runs' provenance. Different seeds will give different cycle counts within the
observed ~0.1% spread.

**Not licensed: relaxing anything about `tab:h3sf`.** W4.3 records that table as
"DATA VERIFIED, ANNOTATION WRONG" with the doc attributing `0f37c28`. That
finding stands, and this memo explains it rather than overturning it — see
below.

## A cleaner statement of "which gem5?"

The `0f37c28` vs `356e7b7d0e` confusion in W4.3 has a plain cause: a gem5 run is
three artifacts with three vintages, and a single commit hash cannot name it.

| artifact | what fixes it | here |
|---|---|---|
| simulator binary | the build, not HEAD | built 2026-08-09, `src/` as of `56874f1d42` |
| Python `configs/` | the working tree at run time | last changed `fa103c5b7b`, 2026-08-19 |
| workload binaries | whenever they were last compiled | verified == committed source at HEAD |

`0f37c28131` (2026-08-18) is the last *content* commit to `configs/`, so it is a
defensible answer for the config tree — which is why W4.3 finds the same
attribution *correct* for `tab:declpredmeas` and `tab:declpredx`. It is the
wrong answer for the workload, because the argv[2] streaming gate lives in
`aggressor.c` and arrived at `356e7b7d0e`. Both hashes were partly right, which
is why the error survived review.

**Owed to edit-queue row 18** (provenance appendix): report the triple, not a
hash. A one-line "gem5 `<hash>`" is not a reproducible statement of apparatus.
