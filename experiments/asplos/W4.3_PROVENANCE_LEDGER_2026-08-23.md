### F3 — `tab:h1bw`: the artifact exists after all, but the metric is wrong

`PAPER_SESSION_PROMPT.md` #26 recorded this table as having "unbound provenance
(date only)". The artifact is in fact on disk: `results/gem5_streaming/REPORT.md`
§1, dated 2026-07-30, carrying all six bandwidths and all six LLC-write counts
exactly as published. It is not in git (`results/`), and the harness that
produced it is gone.

The current-HEAD reconstruction (`GATE1_H1BW_RERUN_OUTCOME.md`) measures
3.19 / 2.76 / 2.41 and 5.12 / 4.04 / 2.41 — i.e. **H2 below WB**, inverting the
published ordering that the table's claim rests on.
`GATE1_H1BW_ANOMALY_RESOLVED_2026-08-18.md` resolves this: at matched work
(`simInsts` within 0.0005%) H2 is **19.3% faster** in cycles while moving 30%
less traffic, so GB/s penalises it for being efficient. The ordering that
matters holds; the *metric* does not.

Consequence for the paper: `tab:h1bw` should not report GB/s alone. Adding a
cycles-to-complete column makes the claim robust to exactly the reproduction a
referee would attempt. Leaving GB/s alone means an honest re-runner gets the
opposite sign.

**F6.1 --- defect. The memory row is wrong.** The table says
`256 GiB DDR + 128 GiB CXL`. Every one of the 214 run directories on this host
instantiates `mem_ctrls[0]` over `0:137438953472` -- **128 GiB** -- and
`mem_ctrls[1]` over `137438953472:274877906944`, another 128 GiB. The cause is
visible in the code rather than inferred: the runs pass
`--mem-size=256GiB --cxl-mem-size=128GiB`, and `configs/ruby/CHI.py:255` does

```python
cxl_bytes  = int(toMemorySize(cxl_size_str))
last       = system.mem_ranges[-1]
dram_bytes = last.size() - cxl_bytes        # <-- CXL is carved OUT of mem-size
```

so `--mem-size` is the **total** address space, not the DDR size. The row
reports the command-line argument rather than the instantiated range, and
therefore over-states DDR by 2x. Correct row: `128 GiB DDR + 128 GiB CXL
(256 GiB total)`.

Nothing measured depends on this -- every working set in the paper is MiB-scale
against a 128 GiB pool -- so it is a disclosure error, not a result error. But
it is exactly the class of error a disclosure table exists to not have, and it
is the only row in the table that was transcribed from an argument instead of
from instantiated state.

**F6.2 --- imprecision. `L1/L2 Stride(4) + DCPT` over-states DCPT.** What is
actually instantiated, per core:

```
cpu[N].l1d.prefetcher.prefetchers[0]  StridePrefetcher  degree=4
cpu[N].l1d.prefetcher.prefetchers[1]  DCPTPrefetcher
cpu[N].l2.prefetcher.prefetchers[0]   StridePrefetcher  degree=4
```

DCPT is on **L1-D only**; L2 has Stride(4) alone; L1-I has no prefetcher. The
row reads as if both levels carry both. `Stride(4)` itself is confirmed
(`degree=4`, 64 entries, 4-way table). The fidelity caveat immediately below
the table says "stride-4 + DCPT" without a level and is unaffected.

**F6.3 --- note, not a defect.** The anchoring row is labelled
`2.6 MiB (~53% LLC)`. The victim argument is `2650` (KiB) against a 5 MiB LLC,
i.e. 2.589 MiB and **51.8%**, and the campaign directories are named `53p`. The
53% label is inherited from the campaign name; 52% would be the arithmetic.
Below the resolution of anything the row is cited for, but if the row is
touched, use 52%.

### F7 --- `tab:appplat`: the Intel column's ways row is true of one of its two hosts

Re-read live on all three hosts today. Confirmed unchanged: sockets/cores
(2x128 AMD; 2x64 / 2x32 Intel), AMD 16 MiB L3 per CCX and 16 ways
(`index3` 16384K, `ways_of_associativity` 16, `cbm_mask ffff`, 16 CLOSes), all
three steppings and microcode revisions, `performance` governor with turbo off
everywhere, CXL presented as a cpuless NUMA node on all three.

**F7.1 --- defect. `LLC ways | 16 | 20 (15 CLOSes)`.** The Intel column heads
two machines, and 20 is true only of the 8592+:

| | `index3/ways_of_associativity` | `index3/size` | `cbm_mask` | `num_closids` |
|---|---|---|---|---|
| 8592+ (mos181) | **20** | 327680K = 320 MiB | `fffff` | 15 |
| 8462Y+ (c4)    | **15** | 61440K = 60 MiB   | `7fff`  | 15 |

The 8462Y+ has **15** ways, not 20. The row is easy to misread because the
8462Y+'s way count and its CLOS count are both 15 -- so the cell
`20 (15 CLOSes)` looks like it already accounts for the second host when it
does not. The `Shared cache` row directly above it *does* split the two hosts
(`320 MB LLC / 60 MB LLC`), which makes the un-split ways row below it read as
deliberate. Correct cell: `20 / 15 (15 CLOSes both)`.

This matters beyond bookkeeping: any CAT way-fraction quoted for work run on c4
is a fraction of 15, not of 20.

**F7.2 --- unit inconsistency, not a wrong number.** The
`CXL capacity / interleave` row reads `252 GiB / not probed` (AMD) against
`256 GiB / 1-way (8592+ only)` (Intel). Both numbers are defensible but they
are measured at different levels:

| host | `cxl list` region | `numactl -H` node 2 |
|---|---|---|
| 8592+ (mos181) | 274877906944 B = **256 GiB** | 258033 MB = **252.0 GiB** |
| 8462Y+ (c4)    | not probed | 262144 MB = **256 GiB** |
| EPYC 9754 (broker) | `cxl list` returns no devices | 258020 MB = **252.0 GiB** |

So the AMD cell reports the OS-presented node size while the Intel cell reports
the device region -- and the 8592+, reported at the same level as the AMD cell,
would read 252 GiB, not 256. The ~4 GiB gap is the kernel's `struct page`
overhead for the region and is expected; the inconsistency is which of the two
the table names. Pick one level and state it in the row.

The same pass closes the note's own admitted gap: c4's CXL node is
262144 MB = 256 GiB (cpuless, node 2). And `cxl list` returning nothing on
broker is re-confirmed, so `not probed` stands.

### F8 --- `tab:fused`'s nine rows were produced by at least two different, uncommitted binaries

Following F1.2 into the raw records turned up something the summary files do
not show. Comparing every benchmark-emitted field (excluding timings, seeds,
addresses and perf counters) across the classes that back `tab:fused`:

```
bsweep_A_bsweep  differs from panel_B16 in: {'no_stream': (absent, False)}
bsweep_B_8way    differs from panel_B16 in: {'no_stream': (absent, False)}
bsweep_B_12way   differs from panel_B16 in: {'no_stream': (absent, False)}
panel_A3_16      differs from panel_B16 in: NOTHING
```

The three `bsweep_*` classes emit a `no_stream` field that the six `panel_*`
classes do not. That is not an arm difference -- it is a **binary** difference:
`cxl_join_bench.cpp:1424` unconditionally prints `"no_stream":...`, so a build
that has the flag always emits it. The panel runs (04:05) came from a build
without `--no-stream`; the bsweep runs (05:30, same morning) came from a build
with it.

`--no-stream` first appears in committed source at `389c9f2` (2026-08-05), a
week after both runs. The immediately preceding commit touching the file is
`f6e15c1` (2026-07-15), which does not have it. So:

- the panel binary matches neither `f6e15c1`'s source (plausibly) nor
  `389c9f2`'s (it lacks `no_stream`);
- the bsweep binary matches no commit at all -- it has `no_stream` a week
  before `no_stream` was committed;
- the two differ from each other.

**Both binaries were uncommitted working-tree state, rebuilt mid-campaign.**
The table presents all nine rows as one experiment; they are two builds an hour
and a rebuild apart. There is no evidence the join kernel itself changed -- the
match count and checksum are identical across both groups, which is a real
constraint -- but "no evidence it changed" is what we have, not "it did not
change", and the binaries are gone.

This also revises F1's phrasing. The problem with the way-sweep rows is not
only that the runner is missing. It is that those three records **carry no
`cmd` field at all**, so unlike every other class in `raw/` there is no record
of the command line either. The CAT mask, the way count, and even whether the
20-of-20 row was a full-mask CLOS or simply CAT torn down are recoverable only
from the filename.

`scripts/run_bsweep_RECONSTRUCTED.py` (added alongside this entry) is the
honest response: the arms those rows must have been, derived from the one thing
the artifacts do fix -- that every recorded benchmark-side field is identical
to `panel_B16`, whose argv *is* recorded -- and labelled a reconstruction in its
filename and its first line so it can never be mistaken for the original.

One thing this pass does *strengthen*: the v1 hash pass covers more than the
`app:kernel` correction below assumed. It is not a small-scale spot check --
`morsel_args`'s own comment says "Correctness is validated once, separately, at
small scale instead", and that comment is wrong. The validation was the full
16-core panel: all twelve join arms, n=30 each, one identical hash and one
identical match count throughout. The correctness claim in the paper is better
supported than the code comment claims; only its *mechanism* description is
wrong.

## Two corrections `app:kernel` needs

Both concern the hash-join kernel appendix, lines 90–94.

1. **"CAT masks are reapplied and read back through `resctrl` on every
   repetition, so a mask silently reset between runs would be caught."**
   Reapplied: true — `run_one` calls `cat_setup(profile)` before every single
   run, from a freshly created group (`setup_b`/`setup_c` call `teardown` first),
   and `set -euo pipefail` plus `sh(check=True)` means a rejected write aborts
   the campaign. Read back: **false** — neither `setup_b` nor `setup_c` reads the
   schemata back and compares; `verify` is a separate manual subcommand the
   runner never invokes; and no raw record carries the applied mask. Accurate
   replacement: *"CAT masks are torn down and reapplied before every single
   repetition, and a rejected write aborts the run; masks were not read back per
   repetition."*

2. **"fused and split configurations must agree on both the match count and a
   running hash of the result tuples."** In the published timing dataset the
   hash was **disabled**: `--result-hash` is absent from every `cmd`, and
   `result_hash` is `0` in all 570 runs. What does agree there is the match count
   (33,427,603) and the result checksum `sum_last_rep` (−369,203), identical
   across every 16-core arm — fused, split, CAT and NTA alike. The tuple hash was
   checked in a separate pass, `results/clos_split/raw_v1_contaminated_with_hash_overhead/`
   (390 runs; re-checked today: one identical hash `7700551460813443366` and one
   identical match count 33,427,603 across all **twelve** 16-core join labels,
   n=30 each, and a second hash shared by the three 1-core labels at the smaller
   fact size; the two hot-probe labels emit none, correctly, since they do no
   join), which was
   discarded precisely because computing the hash contaminated the timings.
   Accurate replacement: *"…must agree on the match count and a result checksum,
   checked per run; a full per-tuple hash was verified in a separate pass whose
   timings were discarded because the hash itself perturbs them."*

Both are cheap fixes and both are the kind of claim a referee can check against
released code in minutes.

### F9 --- the hot table is 256 MiB, not the 170 MB every document claims

Found while pricing a `tab:fused` re-run for W5.1. This is a **disclosure
defect, not a measurement defect**: no measured number changes, but the
geometry attached to every one of them is wrong, and one sentence in
`Sec3_Mitigation` inverts because of it.

`src/cxl_join_bench.cpp:369`:

```cpp
size_t table_capacity(uint64_t hot_bytes) {
  size_t cap = std::max<size_t>(1024, hot_bytes / sizeof(Entry));  // Entry == 16 B
  size_t pow2 = 1;
  while (pow2 < cap) pow2 <<= 1;
  return pow2;
}
```

and `build_table` (`:389`) instantiates the rounded size in full ---
`table.assign(cap, Entry{0,0})` touches every entry, and `nkeys = cap / 2`
fixes the load factor at exactly 0.5. So the *requested* footprint is not the
*resident* footprint whenever the request is not a power of two.

Every published `tab:fused` row requests `--hot-bytes 177838489`
(`scripts/run_confirmatory_panel.py:39`, `scripts/run_m2_sweep.py:26`) =
169.6 MiB = 11,114,905 entries, which rounds to 2^24 = 16,777,216 entries =
**256 MiB**. Ratio 1.5094.

`table_capacity` is **byte-identical** at `f6e15c1` (2026-07-15), `389c9f2`
(2026-08-05) and HEAD, so both uncommitted campaign binaries of F8 rounded the
same way. HEAD differs only by a `HOT_TABLE_ROUNDED` stderr disclosure added
this session (`fef3e5e`). Every raw record stores the request, not the fact ---
which is why this survived four campaigns.

Across the entire raw corpus exactly one `hot_bytes` value is not a power of
two, and it is this one (n=1650 records). The bug therefore has exactly one
victim, and it is the paper's strongest experiment.

**F9.1 --- defect. `Appendix.tex:76`.** "builds an open-addressed hash table
sized to approximately 170\,MB (53\% of the 8592+ LLC)". Both halves are
wrong: 256 MiB, and **80.0%** of the 320 MiB LLC. Note that 53% of 320 MiB is
*unattainable by this kernel* --- the achievable neighbours are 128 MiB (40%)
and 256 MiB (80%). Any re-run must pick one; it cannot pick 53%.

**F9.2 --- defect, and it inverts. `Sec3_Mitigation.tex:92-93`.** "The sweep is
monotonic in ways---even 12 of 20, **more than the hot table's own share**,
leaves it 20\% worse than no restriction." 12 of 20 ways of a 320 MiB LLC is
192 MiB, which is not more than the table's share --- it is **75% of** the
256 MiB table. The clause asserts the opposite of the fact.

The substantive claim survives and is *sharpened*. The table alone needs 16 of
20 ways to fit, so monotonicity below 16 ways is expected rather than
surprising, and the honest statement is that a partition wide enough to hold
the hot table leaves only 4 ways of headroom for everything else --- which is a
better argument for object scope than the inverted one was.

**F9.3 --- label. `scripts/run_m2_sweep.py:30`** labels this value `"170M"`.
Cosmetic, but it is the string that propagated into the prose.

**F9.4 --- the same arithmetic in gem5, in an incomplete campaign.**
`scripts/run_gem5_fused_null.py:40` computes `5 * 1024 * 1024 * 53 // 100` =

## F12 — a correctness flag that does nothing, passed by a runner that believes it does

Found 2026-08-24 while building W7's Knob B and looking for the gate the W7
pre-registration refers to.

`cxl_join_bench.cpp` reads `c.check` in exactly one place: `run_single`, which
computes a `scalar_join` reference over the whole fact array and compares
`matches` and `sum` against it. **`run_morsel` never reads `c.check`.** It emits
`matches_last_rep` and nothing in the binary validates it.

`benchmarks/e2e/hash_join/scripts/run_gem5_fused_null.py:59-60` passes
`--morsel 1m --check` to both the `wb` and the `h2` morsel arms. The flag has
been inert in every morsel run ever made.

**Nothing published is wrong.** The gate that actually operates is cross-arm
equality of `matches_last_rep`, a human comparison, and it holds. The defect is
narrower and is the same shape as F11: an artifact asserts a property that
nothing establishes, and a reader of the runner would conclude the arms are
self-validating.

**Not fixed, and the reason is a rule, not convenience.** Making `--check` live
in morsel mode adds a full `scalar_join` pass, which under gem5 is simulated
cycles ahead of the measured region — apparatus changed mid-campaign beyond the
minimum required to run at all. W7 states its gate explicitly instead
(`W7.1_KNOB_B_2026-08-24.md` §2: 30 configurations, odd `k`, prime morsel sizes
for the tail path, all matching). If the hash_join campaigns are ever re-run
from scratch, the flag should be made live or removed from the runner; leaving a
flag that lies is the worst of the three options.

**Class.** F10 is provenance lost, F11 is a correct artifact unread, F12 is an
artifact read and believed that does not do what it says. All three are failures
of the same kind — the document and the thing diverge — and only the third is
cheap to prevent: a flag whose name is a claim should be tested by the harness
that passes it.

**Cost class.** F10's campaigns cost credibility with a referee. F11 nearly cost
a submission: premise 1 is one of the two load-bearing supports under a decision
to skip Sep 9, and it was false on evidence already in hand. That the conclusion
survives on the other supports is luck, not process.

**Fixes required.**

1. **Sec5.1 extends from figures to claims.** Any assertion about a mechanism's
   effect names the arm *and* enumerates the tables that measure that arm. If
   the enumeration is not written down, the claim is not made.
2. **A campaign's pre-registration must state what already measures the cell**,
   and say why the existing measurement is insufficient. W1's would have read
   "third measurement; existing ones are single-run and have no counters" --
   which is a good justification, and would have produced a better-scoped
   experiment.
3. **`tab:sens` and `tab:h3sf` must cross-reference in the paper.** They share
   an arm and a cell and currently give a reader no way to see it. Edit-queue
   item; the two tables disagreeing by 0.7% is also currently unexplained in
   print.
4. The 0.7% itself is ~14 sd on W1's variance and spans a commit change
   (`b2c6499` -> `356e7b7d0e`) and a harness change (`p1batch.sh` ->
   `sf_inf_cells.sh`). Not noise, not material, and it should be stated rather
   than smoothed.

### The `0f37c28` vs `356e7b7d0e` confusion has a cause worth naming

### One caveat in the ledger's direction is too strong

W1.4 Limit 2, quoted forward into W1.5, says the campaigns are "four days and
one gem5 commit apart." There is no commit between them: HEAD `356e7b7d0e` is
