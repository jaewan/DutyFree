# W8.1 — the pseudo-instruction every gem5 STREAMING number came from is SE-only

Written 2026-08-24, **before T5 runs**, while T4's boot is in flight.
**Source reading, zero compute cost.** Fixes a defect in `w8/t5_analyze.py`
that would have mis-scored one of the three T5 arms, and converts that arm from
a broken one into the strongest control W8 has.

## The finding

`pseudo_inst::setstreaming` (`gem5/src/sim/pseudo_inst.cc:622`) marks pages in
`process->pTable` — the **SE-mode `EmulationPageTable`**. Its first act is:

```c
auto *process = tc->getProcessPtr();
if (!process) {
    warn("pseudo_inst::setstreaming called outside SE mode, ignored\n");
    return;
}
```

There is no full-system branch anywhere in the function. In FS mode the m5op
warns and returns, and no page is marked.

Every gem5 STREAMING number this project owns — W1, W7, `tab:sens`,
`tab:h3sf`, the whole SE corpus — was declared through this instruction. That
is not a problem for those results: they are SE runs, where it works exactly as
intended. It is a fact about what those results **can and cannot** demonstrate,
and W8 was opened precisely to close that gap.

## What it breaks

`w8/rcs/w8_stream_m5op.rcS` runs the benchmark under `--declare m5op` in FS. In
FS that declaration is a no-op, so the arm produces `streamingTranslations == 0`
and `streamingAccesses == 0`.

`t5_analyze.py` decided each arm's expectation by substring:

```python
expect_stream = "mprot" in arm or "stream" in arm
```

`w8_t5_stream_m5op` contains `"stream"`, so the analyzer expected a non-zero
count and would have printed **G1 FAIL, G3 FAIL** for an arm behaving exactly as
the simulator is built to behave. The docstring never claimed otherwise — its
G1 and G3 sections name only the `wb` and `mprotect` arms. The m5op arm was
added to `rcs/` without a pre-registered expectation, and the substring rule
silently invented the wrong one. The pre-registration
(`benchmarks/e2e/hash_join/GEM5_FS_OS_CONTRACT_PREREGISTRATION.md:37`) mentions
the m5op only for the **T2 SE sweep**, where it is correct.

This is **F12** again — an artifact read and believed that does not do what it
says — caught this time before the data existed rather than after.

## What it is worth

Corrected, the m5op arm is a negative control that cannot be faked:

| arm | declares via | `streamingTranslations` | `streamingAccesses` |
|---|---|---:|---:|
| `wb` | nothing | 0 | 0 |
| `stream_mprot` | `PROT_STREAMING` | **> 0** | **> 0** |
| `stream_m5op` | m5op 0x55 | **0** | **0** |

Same guest, same kernel, same binary, same flags, same checkpoint — one
different `--declare`. The simulator-harness path produces nothing; the OS path
produces classifications through a real page table that a real kernel wrote.
There is no way to arrange that outcome by tuning: the zero is enforced by a
null-pointer check in gem5's own source, and the non-zero has to survive the
in-guest PTE readback (G2) independently.

Stated plainly, it is the sentence W8 exists to buy — and the m5op arm makes it
a measured contrast rather than an assertion:

> Every STREAMING result in this paper declares through a simulator
> pseudo-instruction that does not exist outside SE mode. In full system, on the
> same binary, that declaration does nothing at all; the kernel's
> `PROT_STREAMING` declaration reaches the x86 walker and is classified.

**This does not alter any published claim.** The SE results were produced in SE
mode, where the m5op is the intended mechanism, and nothing here says they are
wrong. What it changes is only what the *FS* arm demonstrates. Flagged rather
than acted on beyond the analyzer, per W8's escalation rule.

## Fixes applied

1. **`t5_analyze.py`: an explicit arm table replaces substring inference.**
   `ARMS` maps a directory-name suffix to `expect_stream` and `m5op`. An
   unrecognized directory is reported `UNKNOWN ARM` and left ungated rather than
   guessed at. Suffix matching, so `rerun_w8_t5_wb` still gates as `wb`.
2. **New gate G5**, m5op arm only: gem5's own
   `"setstreaming called outside SE mode"` warning must appear in the run log.
   A zero *with* the warning is a demonstration; a zero *without* it is an
   unexplained zero, and the two must not be reported as the same thing.
3. **`run_t5.sh` tees gem5's stdout/stderr to `<outdir>/gem5.log`.** `warn()`
   goes to stderr and nowhere else; without the tee, G5's evidence would be lost
   the moment the terminal scrolled.
4. **The docstring's G0 section now carries the arm table and the reason**,
   including the instruction that a non-zero m5op result FAILS the gate and must
   not be waved through as good news — it would mean `setstreaming` grew an FS
   path, and every reading here would need redoing.

## Ledger lesson

`w7_analyze.py` and `t5_analyze.py` were both written before their data, which
is the right practice and is why the W7 vacuous-PASS and this mis-scoring were
both cheap to fix. But writing an analyzer early only protects against fishing;
it does not protect against **inferring an experiment's expectations from its
own file names**. Where an arm's expected result is a design fact, it belongs in
a table with the reason next to it, not in a substring test.

Related: the same session's `W7.2` addendum, where a memo's "cannot separate two
readings" turned out to be a property of the columns parsed rather than of the
experiment. Both are the same failure at different layers — the analysis knew
less than the artifacts did.

## Addendum, same day — the two declaration paths converge on one mechanism

The finding above raises the obvious follow-up: if SE and FS declare differently,
do they exercise the same hardware? **They do**, and the convergence point is a
single line. Source reading, zero compute.

`TLB::translate` (`src/arch/x86/tlb.cc:322`) has one TLB-miss handler with a
two-way branch at line 453:

| mode | how `TlbEntry::streaming` is set |
|---|---|
| SE | `tlb.cc:477` — `pte->flags & EmulationPageTable::Streaming`, the bit the m5op sets |
| FS | `pagetable_walker.cc:364` (PMD leaf, PAT selector bit 12) and `:389` (4K PTE, bit 7) — `bits(pte,N) && pte.pcd && !pte.pwt`, i.e. PAT slot 6 read off a real PTE |

Both branches then fall through to the **same shared tail**, and streaming has
exactly one consumer there (`tlb.cc:510-513`):

```c
if (entry->streaming) {
    req->setCacheCoherenceFlags(Request::STREAMING_BIT);
    stats.streamingAccesses++;
}
```

So everything downstream of the TLB — the request flag, CHI, H2, H3, every cache
counter — is byte-identical between the SE corpus and the FS arms. The two modes
differ only in **who writes the bit into the TLB entry**: a simulator
pseudo-instruction reaching into an emulated page table, or Linux writing a PTE
that the x86 walker decodes. That is precisely the substitution W8 was opened to
demonstrate, and it is a substitution of the *declaration* only.

One asymmetry, and it is in the FS path's favour. The walker must also write
`entry.uncacheable = uncacheable && !entry.streaming` (`:365`, `:390`), because
slot 6 sets PCD and PCD would otherwise be read as "uncacheable." The SE path
never faces this: the m5op sets a private flag with no PAT encoding behind it.
The FS path had to solve a problem SE does not have, and solved it.

### Two cautions this establishes

1. **`streamingTranslations` is structurally zero in SE mode** — SE never runs
   the walker. An SE `stats.txt` showing zero is not evidence that a declaration
   failed. `streamingAccesses` is the counter that is meaningful in both modes,
   because it lives in the shared tail.
2. **`streamingTranslations` also counts functional walks.** The increment at
   `pagetable_walker.cc:528` is guarded by `doTLBInsert && entry.streaming` but
   sits *above* the `if (!functional)` block at `:530`. The T5 gates are
   unaffected — an arm expected to read zero has no streaming pages at all, so
   nothing can inflate it — but the **magnitude** must not be reported as a count
   of demand classifications. For the gate this is a distinction without a
   difference; for any sentence quoting the number it is not.

## Second addendum, same day — the rest of T5's analyzer↔artifact contract

Having found one analyzer expectation that had never met the binary, the other
three were checked the same way, before T5 runs. **No gem5 involved.**

| what G-gate needs | where it comes from | verified |
|---|---|---|
| G2 `DECLARE_PTE_READBACK` + `GATE=PASS(slot6=Streaming)` | `cxl_join_bench.cpp:288-293`, one line, `std::cerr` | yes |
| G4 a JSON line starting `{` and containing `"status"` | `run_morsel` → `:1650`, `std::cout`, `…,"status":"ok"}` | yes |
| G4 `W8-RCS-BENCH-EXIT <n>` exactly once | each `rcs/*.rcS`, one `echo` | yes |
| G5 `setstreaming called outside SE mode` | `pseudo_inst.cc:629`, `warn()` → stderr → `gem5.log` | yes |

Both streams reach the console: init is pid 1 with the console on fds 0/1/2 and
`exec /tmp/runscript` inherits them, so `cerr` and `cout` both land in
`system.pc.com_1.device` where the analyzer reads them.

**Every flag the three arms pass is accepted.** `--mode --policy --declare
--fact-bytes --hot-bytes --reps --warmups --probe-batch --json` each appear once
in the parser and once in the guest binary's strings; `--declare` rejects
anything but `m5op`/`mprotect` with `exit(2)` (`:1787`); `--mode morsel`
dispatches to `run_morsel` (`:1815`). An unrecognized flag would have aborted
the arm with `exit 2` before any output, and would have been discovered only
after a full restore.

**The binary in the image is the binary that was checked.** Read out of the
image with `debugfs` without booting it:
`/etc/W8-PROVENANCE` records `bench sha256 270df6dd…c94c7a06`, which is
`sha256sum build/cxl_join_bench.gem5fs` exactly.

### One trap found and left in place

`build/cxl_join_bench` — the **host** build — is dated 2026-08-11 and predates
`--probe-batch`; it exits 2 with `unknown argument: --probe-batch`. The guest
build `build/cxl_join_bench.gem5fs` (2026-08-24 01:22) has it. Anyone reaching
for the host binary to sanity-check a T5 command line will get a failure that
looks like a flag error in the arm and is not. Recorded rather than fixed: the
guest image is frozen for this campaign, and rebuilding the host binary is a
change to apparatus that nothing here needs.

The guest binary itself **cannot** be run on the host — it dies with SIGILL, as
a gem5-targeted build should. That is why this contract was established by
reading the parser and the emitters rather than by executing them.

## Third addendum, 2026-08-24 03:26 — T5's restore path has never been executed, and that fixes the arm order

Checked before starting T5, read-only:

| question | answer |
| --- | --- |
| has `fs_restore_chi_8592.sh` ever produced a run? | **no** — `gem5/logs/fs_restore_chi/` does not exist, in either tree |
| any prior FS run under Ruby/CHI anywhere in the project? | **no** — no `stats.txt` in this tree contains `system.ruby` from an FS run; `logs/gem5_fs_os_contract/` is empty |
| has the launcher been touched recently? | three commits (`44216263e2`, `28639f138b`, `073397a60d`), file dated 2026-08-05 |
| are the two trees' copies identical? | yes, md5 `11fc6b8b…` in both |

So T5 arm 1 is simultaneously the first exercise of an untested launcher, the
first FS + Ruby/CHI run this project has done, and a measurement. Those are
three different things and a failure in arm 1 will most likely be the first two.

**What was verified statically**, since the restore itself cannot be rehearsed
without spending a run:

* memory layout matches the checkpoint. T4 booted `--mem-size=256GiB
  --cxl-mem-size=128GiB`; the launcher's `MEMARGS` defaults to exactly that, and
  carries the comment "Fixed layout, must equal boot". A mismatch here is the
  classic silent-corruption mode on restore.
* CPU count matches. The launcher infers `N` from the checkpoint *name* —
  `case "$1" in *2cpu*) N=2` — and the name is `atomic_2cpu_w8busybox`, so
  `N=2`, equal to T4's boot. Note the fragility: the geometry is carried by a
  substring of a directory name, so renaming the checkpoint silently changes the
  simulated machine.
* `--restore-with-cpu=O3CPU` against an Atomic-taken checkpoint is the supported
  flow; that flag exists for precisely this.
* `-r 1` resolves to `cpt.5548084949500` — see the gate-1 hardening in
  `run_t5.sh`.

**Consequence, fixed here before any arm runs: the `wb` arm goes first.** It is
the control, it needs no streaming machinery whatsoever, and it is therefore the
cheapest possible probe of the untested apparatus. If the restore path is
broken, `wb` shows it without entangling the failure with anything about
declaration, the walker, or PAT slot 6. Running a streaming arm first would
produce a failure that looks like it might be about streaming and is not.

Ordering, then: `wb` → `stream_mprot` → `stream_m5op`. The negative control runs
last because its expected result is *zero classifications*, which is
indistinguishable from a broken run until the other two arms have shown the
apparatus works and the positive arm has shown a non-zero count is reachable.
G5 exists for exactly that reason, but G5 is a corroboration, not a substitute
for having a working positive arm to compare against.
