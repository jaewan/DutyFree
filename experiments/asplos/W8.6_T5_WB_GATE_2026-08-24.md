## 3. Four qualifications. None moves the gate; all bind how T5 may be reported.

**A — the `wb` record misreports its declaration channel, and the analyzer repeats it.**
The JSON says `"declare":"m5op"` for an arm that passed no `--declare`.
`g_declare` defaults to `DeclareVia::M5OP` (`cxl_join_bench.cpp:237`) and line 943
prints it *unconditionally*, while `declare_streaming()` is only ever reached under
`if (c.policy == "stream")` (lines 971, 1092, 1164, 1218, 1360, 1548). The `wb` arm
therefore declared **nothing**; the field is the default of an unused flag. The
control is clean — the reporting is not. The hazard is concrete: `t5_analyze.py`
prints `declare=m5op` on the line directly above `G1 PASS (expected ==0)`, which
reads as *"the m5op declaration produced zero classifications"* — the negative-
control claim that belongs to the **`stream_m5op` arm**, not this one. **Reading
rule: the `declare` field is meaningful only when `policy == stream`.**

**B — T5's full-system runs have no CXL involvement. The fact array is in DRAM.**
`bindpool` is SE-only, exactly as `setstreaming` is: `pseudo_inst.cc:674` logged
`bindpool called outside SE mode, ignored`. The benchmark took the m5op path
(`gem5_bind_pool`, `:332`) and its own record says `"placement": "GEM5 no NUMA
placement check"` — **no `mbind` fallback was attempted and no placement was
verified**. Measured, decisively, at the memory controllers:

| controller | range | latency | bytesRead |
|---|---|---|---|
| `mem_ctrls1` | 4–138.5 GiB | 97 ns (DRAM) | **44,996,288** |
| `mem_ctrls2` | 138.5–276 GiB | **198 ns (CXL)** | **46,208** |

45 MB from DRAM against 46 KB from CXL. The 16 MiB fact array was served from
DRAM. The record's `"fact_node": 2` is what was *requested*, not what was
realized — the same requested-vs-realized trap as [F9.4], in a different field.

This touches **no gate**: G1/G2/G3 ask whether the OS declaration reached the
walker and TLB, which is orthogonal to where the pages live. But it is a
**fourth** independent reason no performance comparison is licensed out of T5,
alongside W8.1 Finding 2's three (FS geometry never calibrated against SE; every
arm `--probe-batch 0`, single-rep and cold; 10 MiB vs W7's 5 MiB LLC). It also
extends W8.1's central result: **the SE-only m5op problem is not confined to
`setstreaming`.**

**C — counts in `stats.txt` are summed across two dump sections and are ~2× inflated.**
The arm calls `m5 dumpstats` and then `m5 exit`, which dumps again; gem5's second
dump is cumulative from the same `resetstats`, so the file holds two full stat
sections (visible as two `simSeconds`: 0.233184 and 0.233720). `t5_analyze.py`'s
`stat_sum` sums every matching line, hence the eight `streamingTranslations` rows
above (4 objects × 2 sections). **Presence gates are unaffected** — 0 sums to 0,
and `>0` stays `>0` — but **no count may be quoted as measured.** When
`stream_mprot` returns a non-zero classification count, the reportable figure is
one section's value, not the analyzer's sum.

**D — `run_t5.sh` exits 1 on a fully successful arm, and its exit code carries no information.**
The background harness announced *"Launch T5 wb arm failed with exit code 1"* for
the run gated PASS above. Mechanism, confirmed by reproduction as a script file
with the same `set -euo pipefail`: the closing
`grep -c "setstreaming called outside SE mode" | xargs …` returns 1 when the count
is 0, `pipefail` propagates it, and `set -e` aborts **before** `exit $rc`. So
`exit $rc` never runs for any arm with zero warnings — `wb` **and**
`stream_mprot`. Only `stream_m5op` will exit 0. Consequence: for those two arms a
genuine gem5 failure and a perfect run both surface as exit 1.

Not fixed. The apparatus rule bars changing apparatus mid-campaign beyond what is
required to run at all, and a wrong exit code does not prevent running; arms 2 and
3 will run the same script that arm 1 did. **Expect exit 1 from arm 2 and treat it
as uninformative** — the evidence is the analyzer's gates.

This is the exact mirror of the F12 in `W8.5`: there the harness reported success
over a killed run; here it reports failure over a completed one. The safe
direction, but it still produced a false alarm within the hour. It is also a
direct vindication of the rule committed in `f47d554`: **gate on a completion
marker the workload itself emits, never on the harness's exit status.**
`t5_analyze.py` does exactly that, and returned PASS correctly.
