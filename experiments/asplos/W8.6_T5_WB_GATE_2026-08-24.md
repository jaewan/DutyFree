## 3. Four qualifications. None moves the gate; all bind how T5 may be reported.

**A — the `wb` record misreports its declaration channel, and the analyzer repeats it.**
The JSON says `"declare":"m5op"` for an arm that passed no `--declare`.
`g_declare` defaults to `DeclareVia::M5OP` (`cxl_join_bench.cpp:237`) and line 943
prints it *unconditionally*, while `declare_streaming()` is only ever reached under
`if (c.policy == "stream")` (lines 971, 1092, 1164, 1218, 1360, 1548). The `wb` arm
therefore declared **nothing**; the field is the default of an unused flag. The
control is clean — the reporting is not. The hazard is concrete: `t5_analyze.py`
prints `declare=m5op` on the line directly above `G1 PASS (expected ==0)`, which
reads as *"the m5op declaration produced zero classifications"* — the negative-
control claim that belongs to the **`stream_m5op` arm**, not this one. **Reading
rule: the `declare` field is meaningful only when `policy == stream`.**

**B — T5's full-system runs have no CXL involvement. The fact array is in DRAM.**
`bindpool` is SE-only, exactly as `setstreaming` is: `pseudo_inst.cc:674` logged
`bindpool called outside SE mode, ignored`. The benchmark took the m5op path
(`gem5_bind_pool`, `:332`) and its own record says `"placement": "GEM5 no NUMA
placement check"` — **no `mbind` fallback was attempted and no placement was
verified**. Measured, decisively, at the memory controllers:

| controller | range | latency | bytesRead |
|---|---|---|---|
| `mem_ctrls1` | 4–138.5 GiB | 97 ns (DRAM) | **44,996,288** |
| `mem_ctrls2` | 138.5–276 GiB | **198 ns (CXL)** | **46,208** |

45 MB from DRAM against 46 KB from CXL. The 16 MiB fact array was served from
DRAM. The record's `"fact_node": 2` is what was *requested*, not what was
realized — the same requested-vs-realized trap as [F9.4], in a different field.

This touches **no gate**: G1/G2/G3 ask whether the OS declaration reached the
walker and TLB, which is orthogonal to where the pages live. But it is a
**fourth** independent reason no performance comparison is licensed out of T5,
alongside W8.1 Finding 2's three (FS geometry never calibrated against SE; every
arm `--probe-batch 0`, single-rep and cold; 10 MiB vs W7's 5 MiB LLC). It also
extends W8.1's central result: **the SE-only m5op problem is not confined to
`setstreaming`.**

**C — counts in `stats.txt` are summed across two dump sections and are ~2× inflated.**
The arm calls `m5 dumpstats` and then `m5 exit`, which dumps again; gem5's second
dump is cumulative from the same `resetstats`, so the file holds two full stat
sections (visible as two `simSeconds`: 0.233184 and 0.233720). `t5_analyze.py`'s
`stat_sum` sums every matching line, hence the eight `streamingTranslations` rows
above (4 objects × 2 sections). **Presence gates are unaffected** — 0 sums to 0,
and `>0` stays `>0` — but **no count may be quoted as measured.** When
`stream_mprot` returns a non-zero classification count, the reportable figure is
one section's value, not the analyzer's sum.

**D — `run_t5.sh` exits 1 on a fully successful arm, and its exit code carries no information.**
The background harness announced *"Launch T5 wb arm failed with exit code 1"* for
the run gated PASS above. Mechanism, confirmed by reproduction as a script file
with the same `set -euo pipefail`: the closing
`grep -c "setstreaming called outside SE mode" | xargs …` returns 1 when the count
is 0, `pipefail` propagates it, and `set -e` aborts **before** `exit $rc`. So
`exit $rc` never runs for any arm with zero warnings — `wb` **and**
`stream_mprot`. Only `stream_m5op` will exit 0. Consequence: for those two arms a
genuine gem5 failure and a perfect run both surface as exit 1.

Not fixed. The apparatus rule bars changing apparatus mid-campaign beyond what is
required to run at all, and a wrong exit code does not prevent running; arms 2 and
3 will run the same script that arm 1 did. **Expect exit 1 from arm 2 and treat it
as uninformative** — the evidence is the analyzer's gates.

This is the exact mirror of the F12 in `W8.5`: there the harness reported success
over a killed run; here it reports failure over a completed one. The safe
direction, but it still produced a false alarm within the hour. It is also a
direct vindication of the rule committed in `f47d554`: **gate on a completion
marker the workload itself emits, never on the harness's exit status.**
`t5_analyze.py` does exactly that, and returned PASS correctly.

## Addendum, 2026-08-24 — arm 2's reading, fixed before arm 2's data exists

Written and committed while `stream_mprot` was still running (gem5 pid 2112150
alive, ~19 min in, `stats.txt` 0 bytes). The provenance is checkable: this
commit's timestamp precedes the run's completion. §6.6 — once numbers are on
disk, choosing between two defensible readings stops being a methods decision.

### What arm 2 must show

**The declared object is 4,096 pages of 4 KiB.** `huge2m` defaults false
(`cxl_join_bench.cpp:88`) and the arm's rcS passes no huge flag, so no
`MADV_HUGEPAGE` or `MAP_HUGETLB` is issued. Morsel declares `fact` only, at full
`fact_bytes` (`:1092`), and `prefault_region()` runs **before** the declaration,
so every page is resident when `mprotect` walks it and no lazy faults follow.

1. **Console.** `DECLARE_STREAMING via=mprotect base=0x… len=0x1000000 rc=0`.

2. **G2 has no innocent failure mode.** The interface is confirmed present in
   the kernel this checkpoint booted: `linux/vmlinux` (mtime 01:10:12,
   unmodified since T4's boot began) is the binary named by both the boot and
   restore `config.json`, and `nm` finds `streaming_pte_query_{open,show,write}`,
   `streaming_pte_query_fops`, and `__initcall__kmod_streaming__429_573_
   streaming_debugfs_init7` — level 7, a `late_initcall`. `CONFIG_PAT_STREAMING=y`
   and `CONFIG_DEBUG_FS=y`; the rcS mounts debugfs. Checked against the built
   binary rather than `.config`, which is 10 minutes *newer* than `vmlinux` and
   therefore not provably the config that produced it.
   **Consequence: a G2 FAIL means the declaration did not reach the PTE. It may
   not be explained away as a missing debugfs file.**

3. **G1 magnitude — `trans > 0` is necessary, not sufficient.** With 4,096
   prefaulted pages declared, a credible per-section count is O(10^3)–O(10^4).
   A single- or double-digit count would score PASS on the gate as written while
   meaning something entirely different: a stray page carried the label, not the
   object. If that is what returns, it is reported as that, and **no claim that
   the object was classified may be made.** Read per section
   (`t5_sections.py`), never as `t5_analyze.py`'s ~2× sum — qualification C.

4. **G3 : G1 coherence.** `streamingAccesses` counts tagged accesses (per load);
   `streamingTranslations` counts walks (per page fill). G3 >> G1 is expected,
   the ratio being loads per page. **G3 ≈ G1 is incoherent** with streaming 16 MiB
   of Fact records and must be investigated before anything is written down.

5. **Row structure.** Arm 1 showed 4 rows per section, all zero. In arm 2 the
   non-zero mass should sit in the data-TLB row(s) of the core running the
   bench; a non-zero instruction-TLB row needs explaining, not averaging.

6. **G4 also certifies the declaration syscall.** `mprotect` failure is fatal —
   `FATAL: mprotect(PROT_READ|PROT_STREAMING) failed` then `exit(12)`
   (`:305-313`). So `W8-RCS-BENCH-EXIT 0` cannot coexist with a refused
   declaration, and **a kernel lacking the feature cannot produce a quiet null
   in this arm.**

### Qualification B is now observed, not inferred

W8.6 §3 argued from source that T5's full-system runs involve no CXL because
`bindpool` is SE-only. The running arm has now said so itself. Console:
`BIND_POOL fact addr=0x7fa295bb1000 bytes=16777216 node=2 pool=1`; teed
`gem5.log:43`: `src/sim/pseudo_inst.cc:674: warn: pseudo_inst::bindpool called
outside SE mode, ignored`. The request is issued and discarded. **No performance
comparison across T5 arms is licensed** — a fourth independent reason.

### G5's mechanism is proven before arm 3 is spent

G5 (arm 3 only) requires gem5's `warn()` to reach the teed `gem5.log`. That is
now established end-to-end on live data rather than assumed: the launcher
`exec`s gem5 with no redirection and there is no `simerr`/`simout`, and the
`bindpool` warning above is a **runtime** warning — emitted mid-simulation, not
at startup — sitting in the teed log. `bindpool` and `setstreaming` have
byte-identical guard structure (`getProcessPtr()` → `warn()` → `return`,
`pseudo_inst.cc:674` and `:629`), so arm 3's G5 will have material.
It is `warn()`, not `warn_once()`, so the count is one per call, not a boolean.

**Corollary for qualification D.** D scoped the useless exit code to `wb` and
`stream_mprot`, and that scoping is correct for a reason worth stating: those
arms produce no `setstreaming` warning, so `grep -c` returns 0 and exits 1,
which under `set -euo pipefail` aborts `run_t5.sh` before `exit $rc`. Arm 3
*will* match, so `grep` exits 0, the script reaches `exit $rc`, and **arm 3's
exit code is gem5's own and does carry information.**
