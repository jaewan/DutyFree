# W8 / T5: the 90-minute tripwire is mis-calibrated, and I am recording why
# BEFORE it fires rather than explaining it away afterwards

Written 2026-08-24 04:55, with the `wb` arm at 1 h 23 m elapsed and its tripwire
due to fire at 05:01. The run is **not touched** (apparatus rule); what is
recalibrated is an *alarm threshold I set*, not the experiment.

## The tripwire as set

"90 minutes with a zero-byte `stats.txt` ⇒ investigate." It was set before any
T5 arm had ever run, as a guard against a restore that boots into nothing —
exactly the failure `run_t5.sh`'s three gates cannot catch, because they all
fire before gem5 starts.

## Why a zero-byte `stats.txt` is the expected state here, not a symptom

`rcs/w8_wb.rcS` dumps stats **once**, at the end:

```
/sbin/m5 resetstats
/root/cxl_join_bench.gem5fs --mode morsel --policy wb ... --reps 1 --warmups 0 --json
echo "W8-RCS-BENCH-EXIT $?"
/sbin/m5 dumpstats          <-- the only dump in the arm
```

There is no periodic dump and no intermediate console output during the measured
region. So "zero bytes and a static console" is precisely what a healthy run
looks like for the whole of its measured region. The threshold was measuring the
wrong thing: it tests *elapsed time*, but what it wanted to test is *liveness*.

## What the run is actually doing (all non-invasive reads)

| | |
|---|---|
| gem5 started | 03:31 |
| last console line | 04:24 — `HOT_TABLE_WARMED pid=88 warmups=0` |
| now | 04:54 |
| process state | `R`, **99.9% CPU**, CPU time 1:22:25 ≈ elapsed 1:22:26 |

The process has spent essentially 100% of its wall clock on-CPU. It is
simulating, not blocked on I/O and not spinning in the guest's idle loop. Restore
+ boot-in + table build + NUMA bind took 53 min; **the measured region has been
running 30 min.**

## What the measured region should cost, derived from data already in hand

The nearest calibrated comparator is W7's `A0_B0_wb_s1`, whose command line is
recorded in `/tmp/w7/A0_B0_wb_s1.cmd`. It is the **same workload shape** — morsel,
`--policy wb`, `--fact-bytes 16777216`, `--hot-bytes 4194304`, `--probe-batch 0` —
and the same 2-core O3 + Ruby/CHI 8592 machine:

```
W7 A0_B0_wb_s1:  --reps 3 --warmups 1  = 4 passes,  hostSeconds 9037  (2.51 h)
                 -> ~0.63 h = ~38 min per pass, in SE mode
T5 wb arm:       --reps 1 --warmups 0  = 1 pass
```

So **~38 minutes is the SE-mode floor for T5's measured region**, before paying
for full system: a real kernel, a real page table, ext2, and device models that
SE does not simulate at all. 30 minutes in is on schedule; the dump is not due
until roughly 05:05, and an FS multiplier of even 1.5–2× puts it at 05:20–05:35.

**The tripwire would have fired at 05:01, on a healthy run, before its earliest
possible dump.** Firing it and acting on it would have destroyed a run that had
already consumed 53 minutes of restore.

## The replacement, stated now so it is not chosen after the fact

The tripwire is replaced by a **liveness** test, which is what it should have
been, with a much longer patience:

1. **Liveness (the real test):** the gem5 process is in state `R`/`S` with CPU
   time advancing. A process that stops accumulating CPU time is hung; one that
   is simulating is not, however long it takes. Checked above: it is live.
2. **Ceiling:** 4 h elapsed with no `W8-RCS-BENCH-EXIT` on the console. That is
   ~6× the derived single-pass estimate plus the observed 53 min of setup, so it
   cannot be tripped by a merely slow run — only by one that is stuck.
3. **Console regression:** the arm must reach `W8-RCS-BENCH-EXIT` before
   `stats.txt` becomes non-zero. If `stats.txt` fills without that line ever
   appearing, something dumped stats that was not the rcS, and the run is not
   the arm it claims to be.

The same three apply to `stream_mprot` and `stream_m5op` when their turn comes.
Their measured regions are the same size; `stream_mprot` additionally pays for
walker classification, which is per-translation and cheap.

## What this does not change

Nothing about the arm, its gates, or `t5_analyze.py`. **G0–G5 are untouched**, and
the standing rule holds unchanged: `stream_mprot` does not start until `wb`'s
gate has been read by `t5_analyze.py` and stated in writing.
